# Todo 验收与交接

状态：0.4.1 起随源码发布（2026-11-07），应用 0.4.3、Skill 1.4.0；实例是否部署以验证记录为准。服务通过 `/meta.agent_capabilities` 中的 `todo-review-v1` 声明支持，旧服务继续沿用原任务操作，不把描述里的验收要求说成已强制执行。

## 使用

任务详情的“任务验收”默认以阅读形式展示，通过“配置验收”填写标准并显式选择一名当前团队成员。可以选择自己，不自动指定负责人或创建新身份。未配置的任务保持原有完成流程。

1. 创建人、负责人或网页管理员按现有任务维护权限配置标准与验收人。
2. 交付准备好后，填写“交付依据”并提交验收。记录提交人、时间和提交版本，不把提交当成完成，也不猜测团队自定义的待验收列。
3. 指定验收人查看原任务、证据及关联简报，选择“通过并完成”，或填写原因后“退回修改”。管理员和创建人不能代替另一个指定验收人作决定。
4. 退回后任务保持未完成；修改、再次提交和后续决定保留完整历史。通过时事务内移动到团队默认完成列，Timeline 简报及 Calendar 仍引用同一任务，不创建副本或自动发布简报。

待验收任务进入验收人的“与我相关／待我处理”，通知仍定位原任务。通过、退回、提交、撤回及失效均保留操作者与历史；同一操作重试不增加第二条决定或重复通知。

## 状态与修改

- `draft`：已配置、未提交。
- `pending`：已提交，等待指定验收人决定。
- `changes_requested`：已退回，保留原因和交付依据。
- `approved`：已通过且任务完成，记录决定人、时间与可选意见。

提交后修改任务正文、标题、负责人、分类、日期、排期、链接等内容，会使当前提交失效并回到 draft，必须重新提交；普通讨论不会自动撤回提交，但决定仍需读取最新任务修订。待验收时修改或移除验收设置需先撤回。通过后修改已验收内容或调整验收设置需先重开；重开清除当前批准并保留既往记录。归档中的任务不能作验收决定，恢复后再接续。

完成按钮、拖到完成列、联合上报中的任务移动、含任务列的“完成列”属性修改与列迁移共用 Go 校验，未通过的验收不能被这些路径绕过。事务冲突时不覆盖其他人的决定，联合上报失败整体回滚。没有验收要求的旧任务仍可直接完成。

## API 与 Agent

沿用 `PATCH /api/v1/todos/<id>`、`operation_id` 和 `expected_revision`，不增加独立身份或权限体系：

| 动作 | 额外参数／权限 |
| --- | --- |
| `edit` | `review: {criteria, reviewer_id}` 配置；未提交状态可设为 null 移除。只接受配置，客户端不能伪造批准或时间 |
| `submit-review` | `body` 为必填交付依据，最多 12000 UTF-8 字节；原任务维护权限 |
| `withdraw-review` | 原任务维护权限，当前须 pending |
| `approve-review` | 指定验收人、todos:read/write、最新 board_revision；body 为可选意见，通过后完成 |
| `request-changes` | 指定验收人、todos:read/write；body 为必填退回原因 |

创建／编辑标准上限 8000 UTF-8 字节。任务范围、成员与凭证身份由 Go 校验；指定为验收人不会扩展 Token scopes，也不赋予普通编辑／转派任务的权限。验收决定是 Todo 操作，不要求借用评论或简报写权限。

内置助手可在确认卡中提交／撤回验收，不提供自动通过／退回工具；人打开原任务完成审阅。外部 Agent 若代表指定验收人调用决定动作，必须已有该人的明确决定授权，不能根据“已交付”状态、测试文字或分配关系自行认定通过。定时助手仍不能修改 Todo 或作验收决定。

P0 增量流、接续上下文和原任务详情自动携带验收变化；接续中标准、证据与意见是摘录，需要验收时回读原对象。Calendar 改期仍复用同一任务，遵守已验收内容的修改规则。未来统计可以从历史事件区分提交、退回、通过与普通完成，不把简报数量当作验收结果。

## 范围

首版为单验收人流程，不提供多人会签、强制职责分离、自动检查 PR／CI、自动验收、升级通知或外部 Agent 调度。来源链接和人工说明是交付依据，服务不宣称已验证链接里的成果。真实模型／跨 Coding Agent 验收、轻量依赖与持久协作委托仍独立推进。
